SUMOCODE · FIELD GUIDE · 2026-08-06 · PRIME AGENT ARCHITECTURE REVIEW

Borrow the control plane, not the engine

runtime boundary → retained agents → durable goals → evidence gates → reviewable learning

Prime Agent's best ideas are not its branding or even its persistent Python kernel. They are the typed mechanisms that separate intent, continuation, proof, and reusable state. SumoCode can import those disciplines while remaining a Pi extension.

Start hereDeepen the seams SumoCode already owns

How do we gain Prime Agent's endurance without turning SumoCode into another full agent runtime?

Keep Pi as the model and agent loop. Keep SumoCode as the retained experience and control layer. Add durable policy around the places SumoCode already owns: its RPC boundary, subagent registry, completion evidence, activity state, and Memory Scriptorium.

The rule we keep
Adopt a Prime mechanism only when it fits behind an existing SumoCode seam. Anything that requires owning providers, the base agent loop, or every tool call belongs upstream in Pi—or stays an experiment.
Block 1Separate seeing work from owning work

Why can Prime Agent survive a closed terminal while SumoCode cannot?

Prime Agent's terminal is a client. A supervisor routes to a resident worker that owns the session, scheduler, kernels and descendants. SumoCode already separates its retained UI from Pi through RPC, but the foreground host still owns the Pi child process. Closing the host ends the work.

That means SumoCode does not need another renderer boundary. It would need an attachable execution boundary: a versioned supervisor protocol, snapshots, replay, leases and recovery. This is architecture, not a background-process toggle.

In our project
src/sumo-tui/rpc/host.ts:614–697 launches and owns the Pi RPC child. src/sumo-tui/rpc/runtime.ts:163–223 owns terminal input and rendering. Preserve this split. If detachment becomes essential, request a resident/attachable lifecycle from Pi upstream—do not quietly build a second Sumo-owned agent runtime.
Watch out
Prime's worker and kernel processes are lifecycle boundaries, not security sandboxes. A SumoCode daemon would inherit the user's permissions and add recovery, update and stale-owner risks.
Block 2Normalize handles; do not fake retained agents

What makes delegation composable instead of a fancy blocking function call?

Prime's recursive call returns an admission handle immediately. The child runs independently and later sends a message or writes an artifact. SumoCode already follows most of this pattern: spawn, check, wait, cancel and list are separate operations, and every child has a typed snapshot.

The safe local step is a unified read-only work-handle projection across host workers, terminal tasks, subagents and refinement jobs. Durable child identity, restored registries, authoritative usage and universal headless follow-up belong in the Pi process that owns sessions. Ask Pi upstream for those contracts rather than scraping JSONL or pretending terminal keystrokes are a protocol.

In our project
src/subagents/manager.ts already tracks snapshots, worktrees and completion manifests. Improve its handles and observability now. Put retained child sessions, stable messaging and authoritative cost attribution behind explicit upstream Pi APIs.
Block 3Make the objective outlive one answer

How do we stop “I wrote a plausible final message” from becoming “the work is complete”?

A durable goal is a small state machine: active, paused, budget-limited, complete or error. It records the objective, usage, elapsed time and continuation count across turns. Ordinary prose cannot complete it; an explicit transition can.

This turns persistence into policy rather than prompt repetition. The model sees the same objective again, but the host owns status and accounting.

In our project
Add a session-owned Goal Ledger beside SumoCode's private activity state. Expose /sumo:goal and a narrow completion tool. Keep continuation explicitly foreground-only while the Pi RPC child is attached.
Block 4Autonomy must stop on proof, not confidence

When should SumoCode inject another turn—and when must it stop?

Keep the goal separate from the continuation policy. An opt-in autonomous policy may continue only while the goal is active, budgets remain and declared quality gates have not passed. A gate is external evidence: a test command, typecheck, lint, artifact checksum or repository state check.

A failed gate returns bounded output for another attempt. An unchanged workspace should not rerun the same failed gate forever. Hitting a limit produces budget_limited, never false success.

In our project
Subagent settlement already builds a completion manifest in src/subagents/manager.ts:540–589. Use the same evidence vocabulary for foreground root goals: command, exit code, bounded output, workspace revision and timestamp.
Watch out
A passing gate proves only what that gate checks. “Tests pass” does not prove the product requirement, security property or visual quality unless the gate actually covers it.
Block 5Let the harness learn—but only through a ledger

How can SumoCode improve itself without silently corrupting future sessions?

Prime's safest idea is a supplemental refinement ledger. A review proposes small edits to prompt notes, memory, skills or agent specifications. Every edit carries evidence, scope, expected outcome, version history and before/after state. The immutable base system prompt is outside the blast radius.

For SumoCode, this should extend Memory Scriptorium rather than introduce invisible self-modification. Automatic review may draft a proposal. Project-wide, personal or executable changes require acceptance; every applied change can be rolled back.

In our project
Memory Scriptorium already provides a human-facing durable-memory surface. Add a Refinement Ledger alongside it: evidence, proposed edit, scope, before/after snapshot, expected outcome, validation and rollback.
Watch out
Never let a model promote transient task state into global memory automatically. Session, project and personal scopes need different defaults and blast radii.
Block 6Adopt context objects; spike the persistent REPL

Which part of the RLM design belongs in SumoCode?

Make large transcripts, tool outputs, repository snapshots and child artifacts addressable data. Give the model stable handles with bounded operations such as meta, slice, search, map, reduce and materialize. The RLM paper's depth-0 results suggest that externalizing context can help even without recursive agents.

Python is not the principle. A persistent kernel is one possible workspace implementation. Preserve Pi's typed tools, add content-addressed context objects first, then benchmark an optional REPL and bounded value-returning model map/reduce on genuinely large-context tasks.

In our project
Prototype a ContextObjectStore with immutable blob handles and bounded inspection. Keep a workspace_eval kernel optional. Compare token use, wall time, success, compactions and hidden-state failures against Pi's normal tools.
AssemblyThe SumoCode control plane

What does the system look like when the useful pieces sit behind existing seams?

The retained SumoTUI client stays in front of Pi. A Goal Ledger and Continuation Policy live in SumoCode-owned state. SubagentManager remains the orchestration core, while evidence gates and refinement proposals feed deliberate completion and learning.

Why the composition compounds
Goals preserve intent, gates preserve truth, retained agents preserve parallel context, and the ledger preserves only validated lessons. Each mechanism reduces a different failure mode; none needs to replace Pi's core loop.
Cheat sheetEvery term, one honest sentence

For explaining the design at a whiteboard without notes.

TermWhat it actually means
control planeThe host-owned state and policy that decides what work exists, continues, stops and persists.
attachable workerAn execution process whose lifetime is independent of any one terminal client.
admission handleA stable identity confirming that child work started; it is not the child's answer.
durable goalAn objective and state machine that survive ordinary answer boundaries.
continuation policyBounded host logic deciding whether another agent turn should be injected.
quality gateAn external check whose result is evidence—not a general claim of correctness.
completion manifestA bounded record of exit state, duration, repository changes and other proof from a run.
Continual HarnessPrime Agent's versioned supplemental prompt, memory, skill and subagent state; not its execution engine.
RLMA model system that treats long context as data in a REPL and may recursively call focused models over slices.
context objectAn immutable large value kept outside chat and referenced through a stable handle plus bounded inspection operations.
persistent REPLA code environment whose variables and helpers survive multiple tool calls and compaction.
