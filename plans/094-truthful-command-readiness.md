## Why this matters

The retained shell paints and accepts typing quickly, but all child-dependent submissions except `/quit` wait behind initial hydration. A normal Herdr launch using the developer's configured session/extensions measured 0.710s to first frame and 8.623s to usable commands: a 7.913s gap. The stripped `--offline --no-extensions --no-session` perf probe measures a different workload. Keep early editing, but name the states accurately and give immediate feedback when a submission is queued behind startup.

## Current state

`src/sumo-tui/rpc/runtime.ts:377-394` emits `boot_screen_frame` + `input_ready` after first render, then `app_ready` + `stable_chrome_ready` from `markChromeStable()`.

`src/sumo-tui/rpc/host.ts:1108-1133` allows `/quit` immediately but otherwise does:

```ts
await hydrationActionGate.whenSettled();
await submitRpcPrompt(message, { visualFixture, scheduler, client });
```

The gate is released only after state/transcript hydration, Activity ownership, autocomplete, and the stable-chrome paint (`host.ts:1883-1900`). `scripts/perf-startup.mjs:379-382` measures the old names. `docs/perf/startup.md` is stamped at an older commit.

## Contract to implement

- `editor_ready`: first retained frame is painted and input can be edited.
- `command_ready`: hydration is committed, deferred child actions drained, autocomplete configured, and a new submission can dispatch.
- Keep `input_ready` and `app_ready` as mandatory deprecated compatibility aliases for one release while all perf consumers migrate; they emit at their historical corresponding points.
- A user pressing Enter before command readiness sees one terse, lowercase status/notification that the command is queued; the text is still submitted exactly once after readiness.
- `/quit`, interrupt, and draft editing remain available before command readiness.

## Steps

### Step 1: Pin state semantics in unit tests

Export a narrow `createEditorSubmitHandler({ gate, notifications, submit, requestExit, isTreeBusy })` (exact name may vary) from `host.ts`, and make `runRpcHost()` consume it. This pure seam is explicitly permitted and is not the Plan 111 host lifecycle extraction. Add tests that prove:
- `editor_ready` emits once after the first retained render;
- `command_ready` is absent until hydration and deferred actions complete;
- command readiness emits once after `markChromeStable`, deferred-action drain, and the gate's `ready = true`, but before queued submit continuations resume;
- a pre-ready submission is retained and dispatched once;
- `/quit` remains immediate.

Prefer an explicit gate readiness query/callback over test-only sleeps.

**Verify**: targeted tests fail under the old names/behavior, then pass after implementation.

### Step 2: Add explicit readiness APIs and diagnostics

Give `InitialHydrationActionGate` a public read-only readiness getter plus its existing `whenSettled()` Promise; the getter becomes true only after deferred intents drain. Add an `onReady` callback to the gate: after the drain loop, set `ready = true`, invoke `onReady`, and only then let the shared `whenSettled()` Promise resolve. Wire that callback to a separate idempotent `RpcHostRuntime.markCommandReady()` method. This guarantees `command_ready` is emitted before any pre-ready submitter awaiting the same Promise resumes. Do not emit command readiness from `markChromeStable()`, which currently runs before gate release.

Emit `editor_ready` from the first-frame location. Keep the old aliases at their historical corresponding points for one release and label them deprecated in code/docs.

**Verify**: runtime and gate tests pass; every readiness event appears once.

### Step 3: Make pre-ready submission feedback immediate

Before awaiting the gate, detect not-ready state and show one bounded notification/status such as `finishing startup · command queued`. Do not duplicate notices for one submission and do not change the submitted text. Preserve startup-safe `/quit` behavior.

**Verify**: host test asserts immediate feedback, no early RPC prompt, and exactly one prompt after gate release.

### Step 4: Update startup measurement and documentation

Measure and report `editorReadyMs`, `commandReadyMs`, and their gap. Update `scripts/perf-real-world.mjs` to prefer the new names while accepting the mandatory one-release aliases. Regenerate the stripped startup report at current HEAD after Plan 093 and label its flags; separately regenerate the normal configured workload only when it can run without exposing credentials. Never compare the stripped numbers to the 7.913s normal-session reproduction as if they were the same benchmark.

**Verify**: `pnpm perf:startup` exits 0 and its Markdown contains both metrics; the real-world parser has a targeted test or successful isolated run using the new names.

### Step 5: Run full runtime gates

**Verify**: all commands in the command table pass, including `pnpm visual:ci`. If feedback changes a captured surface, also run `pnpm visual:review` and attach evidence; do not run `visual:promote`.
