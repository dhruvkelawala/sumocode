1. **Inherited-entry identification and unavailable parents — still open at the readable-but-partial parent boundary.** The original identity/root/missing-parent choices are closed by “entry id present in the resolved parent file”, “inside the resolved root”, and the missing/unreadable/outside-root session being “excluded from `summary` totals” (`spec.md:208–210`). A complete parent with two assistant entries, and a child containing those two ids plus one new assistant entry, produces child `inherited_entries = 2`, child `assistant_turns = 1`, and corpus turns **3**. With the parent missing, the child's three turns remain visible and its summary contribution is **0**. However, “readable” does not settle whether an in-root parent whose bytes are accessible but contain an unparsable line is an admissible identity source: partial files are a separate category at `spec.md:159,173`. If that parent contains a parseable copied id and an unrelated broken line, a child containing that id and one new turn contributes **1** if the parseable parent ids are accepted, versus **0** if a partial parent makes inheritance unverifiable. Specify this composition, not a different inheritance policy.

2. **Polling matcher, suppression granularity and counts — closed.** The contract specifies unquoted separators, an exact `sleep` command name, and first-argument regex `^[0-9]+(\.[0-9]+)?$` (`spec.md:220`), plus “one row per key”, “regardless of count”, and “total occurrences including the first” (`:222`). Also, “per 100 assistant turns” (`:195`) versus summary “total compactions over total turns” (`:235`) leaves a literal **20 versus 0.2** for two compactions and ten turns. Details below.

## Introduced by the fix

1. **Internal composition: the two highlighted interactions agree; the pressure formula does not state the same unit.**

   Inheritance and aggregation agree on contributors: the unverified child is “excluded from `summary` totals” (`spec.md:210`), and summary explicitly names “partial file, unverified inheritance” as exclusions (`:236`). “Sums” at `:232` is not an instruction to re-include excluded sessions. Likewise, streaks are defined over “the accounted sequence (see the model filter)” (`:194`), and the filter explicitly removes the B-success (`:212`). There is no surviving 1-versus-2 streak contradiction.

   The actual formula drift is `compaction_pressure`: “compactions per 100 assistant turns” (`:195`) requires `100 * C / T`; “recomputed as total compactions over total turns” (`:235`), read as written, supplies `C / T`. One contributed session with C=2, T=10 should not have pressure 20 in its record and 0.2 in its summary. Making the multiplier explicit preserves the settled metric rather than redesigning it. The generic “summed counts” test promise does not assert this unit (`:250`).

   There is also a **wrong rationale, not an ambiguous counting rule**, at `:212`: calls without results do have an issuing assistant turn. Pi puts `ToolCall` objects in assistant `content` (`node_modules/@earendil-works/pi-ai/dist/types.d.ts:256–264,307–318`). The explicit instruction to report their count unfiltered remains implementable; “because no issuing turn exists” is only true of orphan results.

2. **Required fields still lack complete numerical definitions; some other fields only lack serialization details.**

   **Model attribution:** `models_by_turn` is named at `spec.md:180`, but its only plan type is `Record<string, int>` (`plan.mdx:212`). Matching “either” id at `spec.md:146` defines a predicate, not an attribution reducer. For a single turn with `model = A` and `responseModel = B`, `{ A: 1 }`, `{ B: 1 }`, and `{ A: 1, B: 1 }` are distinguishable outputs; neither document selects one. The installed message type permits both fields (`node_modules/@earendil-works/pi-ai/dist/types.d.ts:312–313`). This is not merely choosing how to spell a label: the reported count for A changes.

   **Auxiliary availability:** each auxiliary bucket has `reasoning_tokens`, but no unreported-event count (`spec.md:184`); the known-subtotal rule expressly talks about “turns” and its companion is `reasoning_unreported_turns` (`:200`). Compaction and branch-summary `usage` are optional, as is tool-result `usage`; reasoning is optional even within a present usage object (installed `session-manager.d.ts:36–55`; `pi-ai/dist/types.d.ts:265–277,330–337`). For a compaction with input usage 5 followed by a compaction without recorded usage, the contract needs to select **5 as a recorded subtotal or `null` as incomplete input**. “Inputs were partial” (`spec.md:176`) does not define whether the absent optional usage participates in the bucket at all. Similarly, two auxiliary usage objects with reasoning 2 and absent need an explicit subtotal-versus-unavailable rule; the assistant-turn coverage counter does not describe those events. “Aux buckets” are sums (`:232`) only after their inputs and availability have been defined.

   **Shape-only omissions:** `flags.inheritance` has no value definition, and `unknown_entries` appears in both flags and metrics without stating whether the flag repeats the count or indicates its presence (`:172,180`). These are duplicate placements, not evidence of two explicit conflicting definitions. The rule-set value is fixed but its suppression-record member name is not (`:216,222`); `sessions_missing` lacks a placement/schema (`:236`); cache-read share and summary failure rates lack JSON member names (`:199,233`). “Branch summaries ... are therefore `null`” (`:212`) refers to a bucket, not a separately declared top-level metric (`:180,184`); object-null versus null-valued bucket members remains a shape choice. `TokenBucket` and `Location` in the plan can be linked to `spec.md:184,196`; they need not become invented numerical concepts.
