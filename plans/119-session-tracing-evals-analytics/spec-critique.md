# Spec critique — session tracing, evals and analytics

## 1. Verdict

**Not ready, needs reshaping.** The first ablation targets presentation rather than the intended model-facing output, the companion run command disables its required evidence, and the command, measurement and execution contracts still require consequential decisions from the implementer.

Evidence below is from the current working tree and installed Pi 0.85.1 sources, not a rerun of the corpus analysis. `spec.md` and `plan.mdx` references are relative to this directory; other paths are repository-relative. No implementation, test execution, corpus scan, upload or subprocess agent run was performed. This requested critique is the sole write exception to the read-only review.

## 3. Blocking findings

### 1. The ablation can pass its prescribed tests while changing none of the intended model input

**Spec section:** Implementation Decisions → Modules, Decisions (“Tool-result truncation is the first ablation”); Testing Decisions → ablation tests; Out of Scope → retained-renderer behavior (`spec.md:80–84,101–102,120–122,136`).

**What is wrong:** The selected module is an Activity presentation/sanitization helper, not the builtin `bash` output producer. Its callers include `pi-projector.ts`, `feed-publisher.ts` and `background-tasks/task-types.ts`. The shared redaction path also uses it to establish a larger inspection window before redacting a smaller published tail (`src/activity/feed-publisher.ts:275–295`). Replacing its limits globally changes display and potentially redaction behavior, contrary to the renderer non-goal. Changing `logMaxBytes` changes durable terminal-log retention, not the same axis as model-visible output, and still leaves downstream read limits in place (`src/background-tasks/terminal-tools.ts:20–21,53–88`).

`full` also cannot recover information already discarded by Pi's builtin truncation or terminal read windows. A post-result hook can tighten a builtin result; it cannot generically reconstruct all original output. The currently supported result-transform hook is visible in Pi's `dist/core/agent-session.js:244–273`, but using it is a different design decision from extending Activity tails. Re-registering builtins to obtain a different producer would violate `AGENTS.md:119`.

The startup configuration is not implementable as written. The spec supplies no variable names or values; the plan supplies **two numeric-looking variables** (`SUMOCODE_TOOL_OUTPUT_MAX_BYTES` / `_MAX_LINES`, `plan.mdx:294`) while the spec describes arms named by the override's value and gives `HarnessVariant` only one `flag`/`value`. Neither defines `full`'s representation, half-of-25-line rounding, precedence over explicit options, invalid/empty/zero/negative values, or inherited flags in the default arm. Existing `positiveInteger` rejects both zero and infinity and silently falls back (`output-tail.ts:11–12`), so a naive unbounded implementation becomes baseline.

**Why an implementer would fail:** All local truncation tests could pass while the model sees identical builtin output in every arm. Alternatively, the agent could weaken feed bounds/redaction, mutate log retention as a second variable, or override a builtin to force the experiment to work.

**Minimal fix:** Select an actual model-facing axis before building the runner. Either narrow the first comparison to baseline versus an explicitly defined additional result limit through a permitted Pi hook, or obtain a supported upstream producer configuration for genuinely larger/unbounded output. Do not relabel already-truncated output “full.” Publish the exact variant-to-effective-configuration mapping, startup validation/failure rules, covered tool families and unchanged security/presentation limits.

The regression test must observe the **result/context received by the next model call**, using deterministic output above both old limits. Pin independent expected default bytes and metadata, including failed commands, truncation notices, Unicode and empty output. Test unset startup, each valid arm, invalid values and a default arm launched from an environment containing overrides. Preserve redaction and Activity-limit tests separately. Comparing two calls to the newly modified helper is not an independent default oracle.

### 2. There is no self-contained command or analytics-result contract, and the chosen “only entry point” contradicts its consumers

**Spec section:** User Stories 2–16, 40–43; Implementation Decisions → Interfaces/Schema; Testing Decisions → primary seam (`spec.md:32–46,70–73,88–98,114–124`).

**What is wrong:** `scanSessions(root, options) -> CorpusMetrics` names neither the options nor the result schema. The spec never specifies `trace` and `eval` syntax. Even the companion disagrees: Objective uses `eval --fixture <id> --model <id> --harness <variant>` (`plan.mdx:18`), Reports uses `eval <fixture> --harness a,b --reps N` (`:448`). No command-level tests are required. Function tests therefore cannot catch launcher token consumption, failed dispatch, diagnostic text in JSON stdout, wrong defaults or exit statuses.

The analytics “only entry point” is followed immediately by another reader interface; evaluation must consume its reader, and trace assertions need per-run struggle facts. It is unclear whether `CorpusMetrics` retains those facts or only totals. An implementer must either expose internals, rescan temporary directories for a single transcript, or parse it again. There is already a filesystem reader/listing module, including bounded concurrency, at `src/sumo-tui/rpc/session-reader.ts:169–327`. Its list reader intentionally scans only a prefix and is unsuitable for exact totals; its raw-entry reader loads full entries. The plan's “nothing parses Pi” rationale is false. Reuse the safe existing mechanisms where appropriate, but do not import a newly offline analytics layer into the host just to enforce a global one-reader slogan.

Metric definitions also remain measurements chosen by the implementer, not mechanical arithmetic:

- Model/date attribution: first model, last model, or each assistant message? Pi assistant messages already carry `provider`, `model` and optional `responseModel` (`pi-ai/dist/types.d.ts:307–318`), independently of `model_change`. Assigning an entire multi-model session to one group gives different answers. Date could mean header, message time or file mtime.
- Counts/joins: errors divided by calls or matched completed outcomes; orphan and duplicate results; calls with no outcome; all recorded branches versus active context; copied fork ancestry; missing usage versus actual zero. Pi sessions are trees, not just linear conversations (`pi-coding-agent/docs/session-format.md:1–3`).
- Money/tokens: recorded `usage.cost.total` versus recomputation with today's prices; unknown models; cache writes in the input-volume denominator; reasoning as a subset of output, not additive tokens (`pi-ai/dist/types.d.ts:265–285`). Compaction/branch-summary usage and nested tool usage also exist; “every model call” is not an assistant-message-only accounting rule.
- Struggle: a repeated key counted once, occurrences after the first, or combinatorial pairs; consecutive versus anywhere-in-session repeats; error streak scope; detector locations; the precise successful-edit inverse that counts as a revert. `SessionTrace` exposes no complete filesystem history that could establish actual back-and-forth edits from arbitrary shell/write activity.

The spec calls the polling exclusion set contractual but never lists it. The plan's six-name set omits the very `terminal_start` sleep loop cited in its rationale (`plan.mdx:275–279`). Excluding every `terminal_start` would hide real repeated launches; excluding only sleep commands would introduce a heuristic the spec rejects. Also, a repeat detector over all calls does not by itself implement the plan's **repeated failing call** assertion.

**Why an implementer would fail:** Multiple incompatible CLIs and datasets satisfy the prose and selected tests. The scanner can silently change denominator, double-count cached/reasoning tokens or forked usage, or discard the per-session evidence the runner requires.

**Minimal fix:** Add a normative command/JSON contract and a short metric-definition appendix with literal expected examples. Specify root discovery/precedence, recursive scope, filters/grouping, JSON version and missing values, stdout/stderr and exit behavior. Prefer recorded costs for historical accounting; separately label any price-model estimate. Define the polling set and distinguish descriptive repeat signals from failed-repeat scoring. Make the reader private to analytics or explicitly authorize a single-session analysis interface for evaluation; remove the contradictory “only entry point” wording.

Use `bin/sumocode.sh trace --root <temporary-corpus> --json` as the highest acceptance seam, retaining function tests for detailed hermetic arithmetic. Include empty/missing roots, malformed **valid JSON shapes** such as `null`, partial-file diagnostics, model changes/no model-change entry, branches, zero denominators and cache/reasoning accounting. Do not adopt `SessionManager.open` as a read-only scanner: loading older entries can rewrite their source file (`Pi dist/core/session-manager.js:671–678`).

### 3. The eval protocol cannot produce the required transcript or guarantee the advertised isolation

**Spec section:** Solution → Evals; User Stories 17–32; Implementation Decisions → variant/run/fixture records; Testing Decisions → injected runner and end-to-end check (`spec.md:21,47–62,93–96,104–105,109,116,122–126`).

**What is wrong:** The companion's exact run command includes `--no-session` (`plan.mdx:339`). Pi routes that to `SessionManager.inMemory` (`dist/main.js:279–281`); there is no persisted transcript to join. `--offline` only disables startup network operations (`dist/cli/args.js:309`), not model calls, extension effects or network access by tools. Copying the existing subagent spawner unchanged would also be wrong: its generated arguments contain `--no-session --no-extensions` (`src/native-task-config.ts:27`), so it disables both evidence and the SumoCode behaviors being measured.

The seed repository and harness source tree are conflated. The protocol never identifies the repository for `git worktree add`, the fixture's seed baseline, the executable/source provenance, dirty-harness behavior or the final file-diff baseline. Existing `createWorktree` creates a branch in its supplied repository (`src/git/worktree.ts:173–190`); it is not a sandbox. It changes shared Git metadata outside the checkout. Reports are explicitly required outside the checkout too, contradicting the check that **nothing** outside it changed.

A real agent can write to absolute paths, spawn descendants, reach external services and modify its own assertions. SumoCode's memory observer is installed in the headless RPC profile and posts on `agent_end` (`src/extension-core.ts:160`; `src/memory-extraction.ts:69–85`); changing cwd does not isolate that state. The spec supplies no agent-home/resource snapshot, credential policy, tool/MCP/skill configuration freeze, timeout, cancellation/descendant cleanup, partial-result retention or infrastructure-failure status. A cost assertion after completion does not bound spend or stop a loop.

There is no complete fixture manifest. The plan implies `task.md`, `seed/`, `assert.sh`, `fixture.json`, three fixtures and 3–5 repetitions; the spec includes none of those exact requirements. Missing elements include assertion identifiers/types/results, positive-weight constraints, fixture threshold and `>` versus `>=`, shell timeout/environment, trusted assertion location, allowed-file semantics (including untracked/deleted files), and treatment of missing metrics or assertion crashes. The phrase “scores what the agent actually produced” cannot prevent a trivial pass from running a modified `assert.sh` inside the agent's writable checkout.

**Why an implementer would fail:** A mock returns a canned transcript, so the orchestration suite goes green despite a production command that saves none. A live run then hangs, alters user state, evaluates an edited grader, or emits a score with missing evidence. “Same commit/model” alone does not isolate changing user configuration or execution order.

**Minimal fix:** Supply one complete fixture and one exact launch protocol as the normative example. Keep graders outside the agent-writable seed; define immutable seed/harness identities, prompt transport, exact provider/model/thinking/supported sampling controls and allowed resource configuration. Launch the real SumoCode profile with persistence into a unique run-owned session directory/id, and validate the returned transcript rather than searching the user's latest session. Reject unsupported model settings rather than silently falling back.

Define per-run time/spend ceilings, abort and process-group teardown, infrastructure-failure records, private artifact retention and a narrow allowlist of writable run directories. State explicitly whether this is trusted-workspace isolation or an actual security sandbox; withdraw the universal outside-write guarantee if no sandbox is supplied. Grant teardown authority only for runner-owned temporary artifacts, respecting `AGENTS.md:13`.

Keep the injected **whole agent-run adapter**, but test actual filesystem setup and trusted graders with temporary repositories. Require a production-adapter persistence/argument smoke test plus controlled failure/timeout cleanup coverage through the existing integration supervisor. The paid repeated sweep is a separate, opt-in acceptance exercise, not a replacement for those contract tests.

### 4. “Inconclusive” has no algorithm, and event pooling is being asked to justify an inference it does not establish

**Spec section:** Solution → Evals/Reports; User Stories 17, 33–37, 44; Implementation Decisions → small repetition budget, no escalation, separate tracks (`spec.md:21–25,47,63–67,74,101,106–109`).

**What is wrong:** There is no definition of the noise floor, meaningful effect, primary metric, comparison direction, or inconclusive/improved/regressed decision rule. Any colored verdict would be invented. The softened claim in the spec still asserts better resolution from pooling; the plan explicitly promises “orders of magnitude” and says a rate shift is “resolvable” (`plan.mdx:351,383`). Correlation is acknowledged but not handled computationally.

Pooling produces finer **descriptive granularity**, not additional independent experimental runs. Under a simple equal-cluster illustration, 750 events in five sessions have effective sample size approximately `750 / (1 + 149ρ)` for within-session correlation `ρ`; as `ρ` approaches one, that is five, not 750. This is an illustration, not a power estimate for this corpus. No guaranteed resolution multiplier follows. Also, 150 total tool calls per rep are not necessarily 150 **bash** calls.

A pooled rate `Σerrors / Σeligible outcomes` weights long sessions more heavily. Length and tool choice can themselves change under the ablation: a looping arm can contribute many successful reads and dilute its failure rate; an aborted arm can make few calls and appear cheap. A decrease in errors is not by itself an improvement in task quality. `bash.isError` includes deliberately failing probes/tests, not just harness defects. The first-axis rationale uses observational errors without establishing that truncation caused them.

**Why an implementer would fail:** The agent will invent a significance threshold, treat calls as independent Bernoulli trials, compare different tool mixes, omit failed runs or pronounce a causal improvement from one unusually long rep. The plan's ban on displaying a pass fraction is also not a statistical necessity: `k/n` is a valid descriptive summary, just not proof of a reliable pass-probability change at tiny n.

**Minimal fix:** For the first release, make reports descriptive screening reports and label inference inconclusive unless a separately specified rule is met. Compute and retain per fixture/arm/rep: numerator and eligible denominator per tool, repeat/streak facts, task assertion results, cost, completion/infrastructure status and run configuration. Compute pooled rates from counts, show percentage-point deltas and every rep, and represent zero eligible events as unavailable rather than zero errors. Do not pool fixtures or tool families into an unlabeled denominator.

If automated conclusions remain required, specify the estimand, practical effect threshold, run-level/paired analysis, arm-order randomization or counterbalancing, treatment of missing/aborted runs and multiplicity across metrics before collection. Cluster uncertainty at independent runs, not calls; 3–5 runs may simply not support a conclusion. Preserve task-outcome guardrails even when behavior is the headline. Test unequal run lengths, zero-call arms, aborts, conflicting per-rep directions and a pooled improvement driven by one rep. No automatic rep escalation is necessary.

### 5. Publication boundaries are inconsistent, and the share path can leave a raw transcript in the public checkout

**Spec section:** User Stories 29–30, 38–43; Implementation Decisions → export module, telemetry naming, output location, sharing; Testing Decisions → provenance/share tests; Out of Scope → hosted backend (`spec.md:59–60,68–73,98,103–105,111–112,122–130`).

**What is wrong:** Reusing `controls.exportHtml()` **without an output path**, as the companion snippet does, asks Pi to write `pi-session-<session>.html` relative to the child's cwd (`Pi dist/core/export-html/index.js:190–197`). In a public-repository session this produces a raw, potentially secret-bearing artifact in that checkout, not the promised outside-repository state directory. The exported path can also be relative, whereas the uploader is a separate host process. Pi's own sharing path deliberately creates an absolute temporary `session.html` and cleans its temporary directory (`dist/modes/interactive/session-share.js:34–75`).

Export includes the header, **all entries**, active leaf, system prompt and tool schemas (`export-html/index.js:172–188`), not just what is visible on the current branch. A secret gist is unlisted, not private access-controlled storage. The spec never defines whether that full tree is the intended disclosure, how the user is told about it, whether the uploaded file is `session.html`, or what happens on an empty/in-memory session, missing `gh`, expired auth, spawn rejection, timeout, invalid gist URL or concurrent shares. Substituting a successful upload function does not test those cases or the viewer payload. The plan does supply a proposed viewer URL; this must move into the standalone contract rather than remain inferred from rationale.

The analytics export requirement is also unresolved: “inert unless its endpoint variable is set” implies an implemented network exporter, whereas hosted wiring is out of scope. The plan explicitly implements `SUMOCODE_OTLP_ENDPOINT` POSTs (`plan.mdx:157–159,528`). An implementer must decide whether to ship a stub, a local serializer or a sender. No semantic-convention revision is actually pinned, despite that being a decision. Attribute names alone do not define valid OTLP spans, IDs, timestamps, grouping, retry/error behavior or safe content fields; aggregate `SessionMetrics` cannot reconstruct all request spans mechanically.

Fixture synthesis and path scanning are not a proof of confidentiality. Checking only cwd/directory names misses copied identifiers, credentials, URLs, prompt text and grader content; checking every generic directory component also produces false positives. “No identifier from its source session” is not a mechanically decidable acceptance rule without a reference set and a distinction between permitted `source_session` metadata and seed content. No availability/permission contract supplies that private reference data to a future agent or CI.

**Why an implementer would fail:** Sharing can create a commit-ready private transcript in the checkout or disclose abandoned branches unexpectedly; the exporter can exceed scope; a mechanically “clean” synthesized fixture can still contain source-derived material.

**Minimal fix:** Separate `/share` and defer network analytics export from the first slice. For sharing, pin the absolute private temporary export location, gist filename/viewer contract, exact content disclosure, explicit-action behavior, cleanup and failure/cancellation policy. Preserve a usable gist URL after an ambiguous upload result rather than silently retrying and creating duplicates. Test failure paths and no network before invocation; validate the exported payload contract as well as notification dispatch. Escape transcript-derived values in HTML reports and sanitize terminal-facing labels.

Define a private, reviewer-controlled provenance checklist/reference set covering the entire fixture, not just `seed/`, and require human inspection before publishing fixtures. Keep only approved opaque provenance metadata public. If OTLP stays in scope, specify its revision, actual payload/consent/error contract and no-send tests; do not describe it as a future configuration change without that work.

## 4. Non-blocking findings

### 1. Deferred axes describe capabilities the public repository does not own

**Spec section:** Problem Statement; Further Notes → harness dimensions (`spec.md:7,149–150`); companion Layer 2 → The axes.

**What is wrong / implementer risk:** Memory extraction is outbound observation, budget policy is warnings, and compaction state is a reason indicator, as verified above. Treating these as already-existing quality controls invites later flags that only affect display metadata or disable learning rather than recalled context. Skill inlining does exist but is not an interchangeable prompt-composition knob.

**Minimal fix:** Correct the ownership table now and mark future axes “requires seam design.” Keep them out of the first issue's acceptance criteria. This does not require implementing another ablation.

### 2. The latency story and `stalled_turn` detector have no reproducible measurement contract

**Spec section:** Solution → Reports; User Story 37; Further Notes → diagnostics join (`spec.md:25,67,147–150`).

**What is wrong / implementer risk:** A print-mode quality sweep does not run the interactive retained renderer (`bin/sumocode.sh:1105–1112`). Existing diagnostics are not an automatic session/turn join: common records have timestamps but no mandatory session/turn ID (`src/sumo-tui/runtime/diagnostics.ts:67–110`). Classic render samples are thresholded and aggregate on one-second windows (`src/render-diagnostics.ts:35–50,117–127`), so percentiles of slow samples are not percentiles of all renders. The plan adds a turn-over-p95 `stalled_turn` detector but specifies neither the reference population nor how timestamps establish turn start/end rather than idle/user delay.

**Minimal fix:** Explicitly defer the experience track and `stalled_turn` from this slice, or specify a separate real-runtime capture, process/session correlation, timing definitions, missing-data policy and budget. Report unavailable measurements as unavailable. Do not fill the latency panel with print-run wall time and claim renderer contention was measured.

### 3. Historical corpus totals are not a hermetic acceptance oracle, and literal fixtures do not detect upstream drift by themselves

**Spec section:** Testing Decisions → literal transcript fixtures; Further Notes → baseline disagreement means a bug (`spec.md:120–124,142`).

**What is wrong / implementer risk:** The private, mutable default session directory has no frozen file manifest, time cutoff or reader-method revision in the spec. A correct scanner over a changed directory need not return the old totals. Conversely, literal fixtures remain unchanged when a provider changes its emitted shape, so they do not automatically fail on format drift, contrary to `plan.mdx` → Risks → Pi's session format.

**Minimal fix:** Preserve the settled numbers as historical evidence, not a universal hardcoded assertion against a live home directory. Specify a privately held frozen-input manifest and accounting definitions if exact reproduction is required; use public synthetic golden metrics for normal tests. Add a separate pinned-Pi producer/reader contract test and explicit skipped/unsupported-field diagnostics. No new corpus analysis is needed to correct this acceptance method.

### 4. The verification list omits release gates and overstates what the mocks establish

**Spec section:** Testing Decisions → all paragraphs (`spec.md:118–126`); companion Verification → Full gate.

**What is wrong / implementer risk:** The prescribed tests do not cover CLI routing, report JSON/schema/escaping, model/date filtering, actual model-visible ablation, safe upload failures or any OTLP contract. “Pure” tests that write/read files are hermetic filesystem tests, not pure functions. The prohibition on internal call sequences should not prohibit asserting the external process request/environment that defines the experiment. The existing host-action example itself checks both control calls and notification text (`host-actions.test.ts:1623–1624`). Finally, the plan's full gate omits `pnpm visual:ci`, required for SumoTUI/runtime/visual changes by `AGENTS.md:64–69`; HTML output also requires review evidence and no unapproved golden promotion.

**Minimal fix:** Map each retained user-visible decision to an observable acceptance check, including negative cases from the blockers. State the full gate explicitly: `pnpm exec tsc --noEmit && pnpm build`, relevant unit suites, and `pnpm test`, supervised integration and `pnpm visual:ci` for the host/runtime/visual portions. Separate deterministic automated checks from approved, paid sweeps and live `/share` publication smoke tests.

### 5. The self-contained spec drops implementation facts and leaves document authority unclear

**Spec section:** Implementation Decisions → Modules/Schema; Further Notes → companion rationale (`spec.md:78–84,114–116,144`).

**What is wrong / implementer risk:** There is **no literal “no specific file paths” instruction in the reviewed spec**; that suggested contradiction should not be reported as a quotation. The actual omission is that module descriptions identify no ownership locations or existing tests, while the companion has a detailed File map. “Fixture gains” and “SessionMetrics gains” imply existing record definitions that the file map actually introduces as new. Exact fixture count, repetition range, baseline model, polling set, output directory and command forms are left in the rationale rather than the artifact an autonomous implementer is supposed to use alone.

**Minimal fix:** Copy the few normative facts into the spec, distinguish required existing seams from suggested new-file organization, label new schemas as new and declare precedence when companion examples disagree. Do not mandate a large file-per-helper structure merely to replace missing paths.

## 5. Unanswered questions an implementer must invent

1. **Command contract:** Are `trace` and `eval` separate subcommands? Is fixture selection positional or `--fixture`? Does `--harness` accept one name, comma-separated names or repeated flags, and does an unknown name fail before any run? What happens to unknown flags, `--help`, `--json` plus `--out`, failed assertions, incomplete scans and infrastructure failures? Is JSON an object, array or JSONL, with what version, ordering and exit codes? Is native-installed CLI support included or explicitly source-launcher-only?

2. **Corpus/metric contract:** Is the root `~/.pi/agent/sessions`, `getAgentDir()/sessions`, Pi's `PI_CODING_AGENT_SESSION_DIR`, or a CLI override, in what order (`Pi dist/config.js:405–407,421–427`; `dist/main.js:531–534`)? What counts as a session when the header is absent, files are duplicated/forked or all lines fail? Do date filters apply to messages or sessions, inclusively and in which timezone? How are multi-model and no-`model_change` files attributed? Which usage/cost fields, branch entries, orphan outcomes and denominators are included? What exactly constitutes a repeat pair, streak, edit revert and detector location, and which polling names are excluded?

3. **Variant/run identity:** What are the exact variable names, accepted values, defaults, invalid-value behavior, precedence and unbounded semantics? How does a one-flag `HarnessVariant` represent two limits? Is the baseline truly unset even under inherited overrides? Which commit describes the harness versus the seed, and are dirty trees rejected or fingerprinted? What exact provider/model, thinking/sampling settings, Pi version, resource configuration and child-agent behavior are fixed and recorded? How are arm order and caches handled?

4. **Fixture/execution/scoring contract:** What is the versioned `fixture.json` format, threshold comparator, weight domain, assertion result protocol and trusted grader location? How many fixtures/reps are required, how does `min_reps` interact with `--reps`, and what quantitative baseline signal admits a mined fixture? What repository supplies each worktree? Where are transcripts, agent state and artifacts written, what credentials/network access are permitted, and what may teardown delete? What terminates a looping run and its descendants? Are missing evidence, grader errors, aborts and exceeded budgets scores or infrastructure statuses? Is `score` absent/null for corpus-only sessions?

5. **Conclusion/publication contract:** What computation can produce improved, regressed or inconclusive, and for which predeclared metric? Are latency and stalled-turn analysis actually in this slice? Does `/share` upload the entire session tree, header, system prompt and tools, with what warning, absolute export path, filename, viewer URL, failure handling and retention? What does the provenance scan compare against without private source access? Is OTLP a deferred design, local serialization or active sender, and which exact convention revision/content allowlist is permitted?

## 6. Proposed slice split

1. **Offline trace CLI — recommended starting slice; independently shippable.** Deliver a defined `trace --root … --json` contract, shared read-only analysis, explicitly specified core metrics and a minimal terminal summary. Add defined repeat/error detectors as candidate facts, not quality verdicts. Use synthetic inputs for automated acceptance. No live runs, ablation, mining obligation, HTML, OTLP or sharing prerequisite.

2. **One real model-facing ablation — prerequisite for any sweep.** Resolve blocker 1 and prove baseline/variant effects at the next model-input seam, with defaults and security behavior preserved. This can ship independently of the runner. A claim of larger/unbounded builtin output must wait for a permitted producer seam rather than be simulated through display limits.

3. **One-fixture evaluator — depends on slices 1 and 2.** Add a complete manifest, trusted deterministic assertions, isolated run resources, exact persisted-session attribution, supervised lifecycle and score/metrics JSON. Establish the execution mechanism with a synthetic test fixture; this is not a claim that the product's mined fixture corpus is complete. Use the mechanism to validate one approved mined fixture, then add the remaining approved fixtures. Mining three fixtures before having any way to validate them reverses the dependency.

4. **Repeated comparison and review page — depends on slice 3.** Pin repetition/order/aggregation rules; report all reps, denominators, failures and descriptive deltas without unsupported inference. Add the Blueprint HTML page and required capture/review evidence. Keep renderer-latency measurement and OTLP as separately specced follow-ups, not hidden prerequisites.

5. **`/share` — independent of slices 1–4.** Reuse existing RPC export with a private absolute temporary file, explicit disclosure and robust upload handling. Follow host-action tests and the real export payload contract. This should be its own issue because it introduces outbound content publication but needs no analytics reader, fixtures or sweeps.

## 7. Seam assessment

**Recommendation: make `bin/sumocode.sh trace --root <dir> --json` the primary acceptance seam, not `scanSessions` alone.** It is the highest available seam for the user-facing contract and covers launcher dispatch, argument handling, discovery, parsing, aggregation, JSON output and exit status together. `test/integration/launcher-runtime-selection.test.ts:122–180` already supplies a command-level precedent; use supervised infrastructure wherever a real Pi process is involved.

Keep `scanSessions` as the shared in-process analytics interface and retain focused hermetic tests there. Moving every arithmetic edge case into expensive end-to-end subprocess tests would add cost without additional assurance; conversely, exclusively testing the function leaves the actual deliverable untested. The CLI is an acceptance seam, not something the eval runner should shell out to just to reuse parsing.

Remove “only entry point” as a dogma: either return the per-session detector facts required by evaluation through the analysis result, or explicitly expose single-session analysis alongside corpus scanning. Do not export every parsing/detector helper for tests. The existing `session-reader.ts` is prior art worth reusing or narrowly extracting, but its prefix metadata scan is not an analytics engine, and its full-entry reader retains payloads the scanner may not need. Any shared primitive must remain analytics-independent so the interactive host does not import the offline feature.

The injected whole agent-run adapter is a justified seam: the real adapter incurs model spend and process effects; a canned transcript adapter exercises orchestration deterministically. It does **not** substitute for production-adapter persistence/configuration/cleanup tests. Existing worktree helpers are reusable only after the seed-versus-harness repository and teardown ownership are fixed. Existing subagent spawning is not a drop-in eval adapter because its flags disable extensions and persistence.

Finally, the named truncation seam is wrong, not merely too low. Choose a permitted Pi model-result seam for additional limiting or a supported producer configuration for larger output. A lower-level Activity-tail test cannot establish the experiment's treatment. These are the minimum distinct interfaces needed to verify the command, the shared analysis, real agent execution and the actual ablation—fewer than the spec's file-by-file surface, but more than its function-only acceptance story.
